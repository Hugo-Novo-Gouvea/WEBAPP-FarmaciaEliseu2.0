    interface de rede, não só loopback).
  - backend/FarmaciaEliseu.Api/Program.cs: CORS de WithOrigins("localhost:5173")
    para AllowAnyOrigin() (uso interno de rede local, não exposto à internet).
  - frontend/vite.config.ts: adicionado "host: true" no server (aceita
    conexão de outros PCs, não só do próprio servidor).
  Validado acessando pelo IP da máquina (simulando outro PC) — funcionou.

Pendências / riscos conhecidos, pensando no porte do negócio (comércio
pequeno, cidade de ~20 mil habitantes, sem equipe de TI própria):

  ALTA prioridade:
  - Sem backup do banco Postgres. Se o disco da máquina que hospeda o banco
    falhar, os dados (vendas, clientes, fiado) se perdem. Precisa de uma
    rotina de backup (mesmo que simples, tipo pg_dump agendado).
  - O sistema todo depende de UMA máquina ficar ligada (a que roda o backend
    + Postgres). Se essa máquina travar/desligar, nenhum PC consegue vender.
    Vale decidir qual computador vai ser "o servidor" e deixá-lo sempre ligado.
  - Backend (dotnet run) e frontend (npm run dev) ainda estão rodando em modo
    de desenvolvimento, não como um serviço de produção real (não reinicia
    solozinho se cair, não inicia com o Windows). Para uso diário de verdade,
    isso precisa rodar de um jeito mais robusto (serviço do Windows, ou pelo
    menos iniciar automaticamente e reiniciar se travar).

  MÉDIA prioridade:
  - Tela de Produtos ainda busca as ~59 mil linhas de uma vez (sem paginação
    no backend, diferente de Movimentação/Contas a Receber que já corrigi).
    Testado agora: ~1,8s para carregar nesta máquina (rápida, rede local sem
    latência) — num PC mais antigo ou rede mais lenta pode demorar bem mais.
  - Não existe forma de cancelar/corrigir uma venda já finalizada. Se o
    vendedor errar um item ou a forma de pagamento, hoje não tem como
    desfazer pela tela.
  - Sem login/usuário e senha: qualquer pessoa no computador pode escolher
    "ser" qualquer funcionário na lista, sem senha. Não há como saber de
    verdade quem realizou cada venda. Para um comércio pequeno e de confiança
    isso pode ser aceitável, mas é uma decisão consciente a se tomar.

  BAIXA prioridade / FYI:
  - A tabela produtos não tem coluna de estoque/quantidade — isso já vinha
    assim do banco antigo, não fui eu que tirei. Ou seja, o sistema não
    controla quanto tem de cada produto; vender não baixa estoque nenhum,
    porque não existe estoque cadastrado.
  - Agente de impressão (print-agent) funciona tecnicamente (testado com o
    simulador "Microsoft Print to PDF"), mas ainda não foi testado em uma
    impressora térmica física de verdade.
  - Sem testes automatizados (unitários/integração) no projeto.

     clientes diferentes"). Criado frontend/src/utils/errors.ts
     (getErrorMessage) e aplicado em todas as telas/hooks que chamam a API
     — agora a mensagem real do servidor aparece na tela sempre que ela
     existir, com um texto genérico só como último recurso (e uma mensagem
     própria para "sem conexão com o servidor").
  2. Bug real encontrado: frontend/src/pages/Home.tsx não tratava erro
     nenhum na chamada do dashboard — se falhasse, ficava "Carregando..."
     para sempre, sem avisar nada. Corrigido.
  3. Impressão: frontend/src/printing/agente.ts agora repassa o motivo real
     de falha do agente local (ex. impressora não encontrada) em vez de um
     "Falha ao imprimir" genérico; diferencia também "agente não está
     rodando" (erro de conexão) de "agente respondeu com erro".
  4. CONCORRÊNCIA (dois usuários mesma operação ao mesmo tempo) — os 2
     pontos que envolvem dinheiro e SÓ deveriam acontecer uma vez:
     - POST /api/movimentos/{id}/marcar-pago
     - POST /api/itensreceber/quitar
     Antes: liam o registro, conferiam "ainda não pago?" em código C#, e só
     depois gravavam — clássica corrida (TOCTOU): se duas pessoas clicassem
     ao mesmo tempo (ex.: duas atendentes, dois computadores, no mesmo
     cliente), as duas passariam pela checagem e as duas gravariam, podendo
     no caso do "Abater Itens" até gerar DOIS lançamentos de "Resto de
     Conta" pro mesmo cliente.
     Corrigido: a checagem "só se ainda não foi feito" agora é uma única
     operação atômica no banco (EF Core ExecuteUpdateAsync com WHERE
     data_pagamento[_item] IS NULL, dentro de transação). Quem chega
     primeiro grava; quem chega depois recebe HTTP 409 Conflict com uma
     mensagem clara em vez de duplicar o lançamento.
     Testado de propósito disparando 2 requisições literalmente ao mesmo
     tempo (curl em paralelo) contra o mesmo movimento e contra o mesmo
     item — nos dois casos, uma teve sucesso (200) e a outra recebeu 409
     com a mensagem certa. Revertido depois do teste.

  - Segurança: sem autenticação nenhuma (já registrado antes) — combinado
    com CORS liberado (AllowAnyOrigin) e o backend agora aceitando conexão

    computadores), significa que qualquer pessoa com acesso à rede local

    original, não um bug — preserva o "retrato" da venda no momento em que
    aconteceu, mesmo que o cadastro mude depois. Só vale lembrar que, se
    editar o nome de um cliente, vendas antigas continuam mostrando o nome
    antigo (é o esperado, não um erro).
  - Alguma duplicação de código entre as telas de listagem (Movimentação,
    Contas a Receber, Cobrança compartilham uma estrutura bem parecida de
    busca/paginação/tabela) — funciona bem, mas poderia virar um componente
    único no futuro se ficar difícil de manter.
  - Sem testes automatizados no projeto (mencionado antes também).
  - Sem HTTPS — tráfego em texto puro dentro da rede local. Risco baixo se
